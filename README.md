# doc-writing

把设计文档、调研报告、技术方案从"覆盖一切的长文"变成"可决策的短文档"。

AI 写的文档又长又散，不是文笔问题，而是一份文件同时满足多种读者，并用覆盖代替取舍。这个方法做三件事：先判定类型，再用结论与结构物定骨架，最后按可观察判据删。

## 解决什么问题

| 症状 | 本方法给的动作 |
|---|---|
| 文档太长，读者读不完 | 长度预算按读者定；删节测试逐节问"删了它决定会变错吗" |
| 一份文件里什么都有 | 一文件一类型，混装就拆 |
| 读完不知道要决定什么 | 首段一句话结论，含对象、判断、条件 |
| 每段都像 AI 写的 | 六项失败签名，逐项定位到句子 |
| 不知道写完了没有 | 报告层逐行填，缺行即未完成 |

## 什么时候触发

用户说"写设计文档""写调研报告""技术方案""RFC""评审材料"，或说"文档太长""重点不清""AI 味""帮我把这个整理成文档"时触发。

不用于营销文案、翻译、纯格式排版。用户只是问"怎么写更好"且没有给出材料时，直接回答，不走流程。

## 30 秒用法

```text
按 doc-writing 把这份方案改成能评审的文档。
读者是架构组，要在 A 和 B 两个方案里选一个。
```

返回三样东西：

1. 一句话结论，放在第一段。
2. 决策文档的骨架：第 2 段给结构物（部件与连接），再排问题与约束、目标与非目标、方案、取舍、已否决方案。
3. 报告层 7 行检查记录：类型、结论、读者与决定、删减、证据强度、未验证、私有条件缺口。

原文里的教学段与参考段会被删掉，或拆成单独的文件。报告层写在对话里，不写入文档；正文不出现类型、读者、删减记录与证据等级标签。

## 目录结构

| 路径 | 内容 |
|---|---|
| `SKILL.md` | 运行时入口：P0 探针、五类文档门禁、结构闸、删减闸、AI 味六项、报告层 |
| `references/` | 按需加载的判据与反例，加载表在 `SKILL.md` §9 |
| `docs/` | 设计理由、产出流程、门禁、术语、ADR |
| `evals/` | 行为用例与触发判定用例模板；不参与自动测试，仅在用户明确要求时手动运行 |
| `scripts/` | 结构门禁、术语表、预算 |

## 维护

```sh
python3 scripts/check.py --all           # 8 个结构 gate，提交前必须通过
python3 scripts/check.py --only terms    # 单跑一个 gate
python3 scripts/test_gates.py            # 破坏每条规则，确认 gate 会失败
# evals/ 不自动运行：仅在用户明确要求时手动执行用例
```

产出流程见 [docs/authoring.md](docs/authoring.md)，门禁清单见 [docs/verification.md](docs/verification.md)，设计理由见 [docs/design.md](docs/design.md)，术语见 [docs/glossary.md](docs/glossary.md)。

## 版本策略

版本号遵循语义化版本。类型集合、三闸顺序、报告层字段、触发方式任一变化属于 major；新增门禁条目或术语属于 minor；只改措辞属于 patch。major 只在维护者明确要求时升。

版本号写两处：`SKILL.md` 的 `metadata.version` 与 [CHANGELOG.md](CHANGELOG.md) 顶部条目，由 `version` gate 比对。
