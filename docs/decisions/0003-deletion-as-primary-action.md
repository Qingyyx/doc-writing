# 0003 删减为主动作

- 状态：已接受
- 日期：2026-11-01

## 背景

"再精简一下"不是动作，是愿望。它没有对象（删哪节）、没有判据（删到什么程度算够）、也没有记录（删了什么）。结果是每次修改只增不减：新内容加进去，旧内容找不到删除的理由。

AI 生成的文本放大了这个问题。生成成本低，段落看起来都成立，于是保留的默认值变成"全留"。篇幅随版本增长，读者的阅读预算不变。

## 决策

写完必须删，删减是交付前的固定步骤，不是可选优化。删减由五个可观察判据驱动：删节测试、重复检测、密度检测、长度预算、混装检测。删减结果写进报告层：删了几节、几段，结论是否变化。判据见 [SKILL.md](../../SKILL.md) §4。

删节测试是主判据：逐节自问"删了它，读者的决定会变错吗"。答不出就删。其余四项处理答得出但表述冗余的情况。

## 后果

每份文档在交付前都有一轮删除，篇幅下降，承重节更突出。删减记录可审计，读者能看到作者主动放弃了什么。

代价是删减需要判断力：删错承重节会让结论无法成立。处理方式是先跑删节测试再动手，删完重读首段，确认结论没有失去支撑。

## 备选方案

- 设字数上限：上限只说"太长"，不说删什么；作者会压缩措辞、合并句子，承重节的稀释没有解决。
- 让作者自行判断是否精简：不可观察，长文与短文都叫"改过了"，失败没有信号。
- 生成后自动摘要：摘要保留信息密度最低的通用句，删掉细节与数据，反而让文档更不可用。
- 只做重复检测：重复只是五个判据之一，去重后仍可能保留大量与决定无关的节。
